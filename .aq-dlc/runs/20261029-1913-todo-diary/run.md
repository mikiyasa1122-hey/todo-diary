## 01 要求と成功条件
依頼: TODOアプリ。必須は「毎日の日誌更新」「カレンダーによるタスク管理」。完成条件は「TODOとして機能」「バグが起きない」。技術スタックはおまかせ、GitHubは public。
要求 R1〜R6（詳細は state.json）: タスクCRUD / 月カレンダー＋期限切れ一覧 / 1日1件の日誌 / 不正入力で壊れない / 永続化 / ローカル利用の安全性。

### 仮定
- 1人で自分のPCで使うローカルWebアプリ。ログイン機能なし（127.0.0.1のみで待ち受け）。
- タスクは必ず期日（1日）を持つ。時刻・繰り返し・優先度は対象外。
- 日誌は1日1件。未来の日付には書けない。空で保存すると削除。
- カレンダーは日曜始まり、6週固定。「今日」はサーバーのローカル日付。
- 年は 1900〜2999 に制限（日付計算の桁あふれ防止）。
- GitHub公開は gh CLI が未インストールのため実施できず、ローカルgitのみで進めた。
- このPCに Node.js がなく gh もないため、追加インストール不要な Python 標準ライブラリ構成を選んだ。
- gitのユーザー名/メールが未設定だったため、リポジトリ内だけに mirai / アカウントのメールを設定した。

## 02 Failure First
- 日付の検証漏れ（2/30、全角数字、うるう年）→ 単体テスト
- 部分更新で他項目が消える・存在しないIDが成功扱い → Store/APIテスト
- カレンダーの月境界（うるう年、年跨ぎ、日曜始まり月、6週必要な月）→ 境界値テスト
- 壊れた/巨大/深い入れ子のJSON、ランダム入力で500 → ファズテスト（300件）
- 同時書き込み → 20スレッド並行テスト
- 他サイトからの書き込み（CSRF/DNSリバインディング）、XSS、パストラバーサル → HTTPテスト＋app.jsの静的検査
- JS実行環境がないので、画面のIDとJSの参照の整合を静的チェックし、さらにブラウザで手動確認

## 03 設計・実装
- Python 3.14 標準ライブラリ（http.server + sqlite3）＋素のHTML/CSS/JS。依存ゼロで `python -m todo_app` だけで動く。検証は unittest / ruff / mypy --strict（.venv に開発用だけ導入）。
- カレンダーのマス計算はサーバー側（Python、テスト可能）に置き、JSは描画とAPI呼び出しだけにした。
- DBは操作ごとに接続を開くWALモードのSQLite。並行アクセスで共有状態を持たない。
- 書き込みAPIは Content-Type: application/json 必須＋Origin/Sec-Fetch-Site 検査、全リクエストで Host 検査。
- ブラウザで手動確認（追加・完了・編集・削除・日誌保存・未保存確認・未来日の無効化・期限切れ一覧・月移動・スマホ幅）。
  - 発見したバグ: タスク保存中にEnterで次のタスクを追加すると無視され、保存中に入力した文字が残る/連結される。→ 送信時にすぐ入力欄を空にし、失敗時だけ戻す方式に修正し、再確認済み。
